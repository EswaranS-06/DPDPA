# ADR-0008: Process-focused record of processing, with Excel export and import (C21)

Date: 8 Oct 2026. Status: accepted by the build; ComplyX's legal review of the RoPA answer lists and every catalogue process's RoPA defaults is pending.

ComplyX asked for the record of processing (RoPA) to follow its template: one row per processing activity, not per department, using the process catalogue. Its fields combine ComplyX's RoPA template (activity, purpose, legal basis, data principals, personal data, source, internal and external recipients, retention, security, cross-border transfer, consent status, last updated, owner) with its process sample (department, system, processor, deletion), answered as simply as the sample does: "Employee", "Name, PAN, bank details, salary information", "Payroll provider", "RBAC, encryption, logging". The answers should come from the knowledge base, many processes must be recordable without editing each one, and the RoPA and the data element listing must round-trip through Excel: export a workbook whose dropdowns hold the knowledge base's answers, edit it, import it, and keep the data normalised.

| # | Decision | Why | Consequence |
|---|---|---|---|
| 1 | **A processing activity is one RoPA row**, owned by a department and usually started from a catalogue process: name, purpose, lawful bases, law relied on, data principals, personal data, sources, systems, internal recipients, processors, other recipients, retention, deletion, security measures, cross-border transfer and countries, consent status, owner and notes. Numbered PA-001 within the client | The RoPA records processing, which a department may do several times over; ComplyX's template and sample are per activity | `processing_activity` and `processing_activity_element` (migration 0021), under row-level security like every client table |
| 2 | **The knowledge base holds the answers.** Ten vocabularies, `ropa-fields`, `ropa-data-principals`, `ropa-sources`, `ropa-recipients` (each with its usual role, processor or recipient), `ropa-systems`, `ropa-retention`, `ropa-deletion`, `ropa-security` (against Rule 6(1)(a)-(g)), `ropa-consent-status` and `ropa-data-element-names` (a short name for each of the 217 data elements), each listing the other spellings an import accepts | Simple answers, the same across clients, editable by ComplyX in the knowledge-base editor | Drafted by `kb-content` and awaiting legal review. Retention periods cite only what the knowledge base is sure of (Companies Act s.128(5), CGST Act s.36, PMLA s.12, CERT-In 2022, DPDP s.8(7), R8); a client's sector adds its high-confidence retention anchors |
| 3 | **Every catalogue process carries RoPA defaults**: purpose, data principals, personal data (element codes), sources, kinds of department receiving it, processors, other recipients, retention, deletion and security measures, as new `ropa_*` columns of `process_template`, shown in the process editor and its body | The catalogue already knows how a payroll or a CCTV process usually works; starting from it saves typing every answer | All 136 processes have them (TC-C21.1-01). `kb-content` fills them only on a process that has none, so a person's edits stay |
| 4 | **Answers are normalised on the way in, the same way from the form and from Excel.** Closed lists (department, lawful basis, data principals, sources, deletion, cross-border transfer, consent status, internal recipients, catalogue process) refuse anything else; open lists (systems, processors, recipients, retention, security, owner) keep other text as typed and say so. "A; B" and, where every part is an answer, "A, B, C" read as several | Stored values are the knowledge base's answer text, so reports and filters work; named vendors and systems still fit | One normaliser (`ropaKb.ts`), pure, used by the server and the form (TC-C21.2-01) |
| 5 | **Many processes in one step.** The catalogue page ticks each department's usual processes (by the department's kind and name, common and sector processes) and adds them all, each with its defaults; a department that already records a process keeps its activity. Internal recipients such as "Finance" become the client's matching departments | Adding and editing dozens of activities one by one was the stated problem | Review then happens in the activity form or, faster, in Excel (TC-C21.2-02) |
| 6 | **The RoPA and the data element listing export with dropdowns.** A Read me (with the client ID), the data sheet and a Lists sheet; every answer column has a dropdown pointing at its list. Closed single answers are strict; fields that take several answers use a dropdown that also accepts a typed list, since Excel has no multi-select without macros | Macros (.xlsm) are a security risk ComplyX's clients would block; a typed list with the knowledge base's spellings is read back exactly | TC-C21.3-01. 200 empty rows carry the dropdowns for new activities |
| 7 | **Import checks first and saves only what was checked.** The file is read into a list of changes (add, change, remove) with errors and warnings by row and column; nothing is saved until the same file, with the same changes (a fingerprint), is confirmed. A file with any error, another client's workbook, or a changed record saves nothing. Rows taken out of the sheet are left alone; only "Remove" deletes | A bulk edit must never surprise; a stale or wrong file must not overwrite the record | TC-C21.3-02 and TC-C21.3-03 |
| 8 | **Activity numbers are never reused** (a per-client sequence starting above any number in use) | An old export naming PA-002 must not change a newer activity that took a freed number | Removed numbers stay unused |
| 9 | **An activity's personal data joins its department's data elements.** Saving or importing an activity adds the elements the department doesn't list yet, with the department's own category and level where it has one | The data element listing stays the full inventory the RoPA draws on | The data map counts and flows come from activities and the listing together (TC-C20.3-01) |
| 10 | **The per-department processing record is retired.** Migration 0021 moved each department's record into one activity ("HR processing") with the department's elements; the department page now lists its activities instead. `department_data_profile` stays, unused, until a later clean-up | Two places for the same answers would disagree | Nothing recorded before was lost |
| 11 | **The data flow diagram is drawn from the RoPA, never by hand**, in data flow diagram notation with React Flow (`@xyflow/react`): external entities (data principals, other sources such as a KYC registry, processors, recipients, departments receiving the data), processes (the activities, inside their department's box), data stores (the systems, open at both ends) and "Outside India", with a line for every flow coloured by the most sensitive data it carries. The layout is computed in columns, the same for everyone; the page narrows it to one department, hides the data stores, shows what flows on a picked box or line, and downloads it as a PNG. The flows are also a table on the page and a "Data flows" sheet in the RoPA workbook | The DPDP Act and Rules don't prescribe a data map or diagram, but one supports the notice's itemised data and purposes (s.5), accountability and safeguards (s.8(1), s.8(5), Rule 6), transfers (s.16) and a Significant Data Fiduciary's DPIA and audit (s.10(2)). Drawn from the RoPA, it can't drift from it | Change an activity and the diagram follows (TC-C20.3-01, TC-C21.5-01). The earlier SVG flow chart, drawn from department answers, is gone |
