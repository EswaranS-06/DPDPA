# ADR-0010: The document pack is built on ComplyX's DPDP template library

Date: 17 Oct 2026. Status: accepted by the build. ComplyX's counsel still has to review the library: its README asks for the clauses marked VERIFY to be re-checked against the Gazette copy before release to any client.

On 16 Oct 2026 ComplyX gave DUATF its own template library: `Templater-DPDP` v1.0 of 15 Oct 2026. It has 37 Markdown templates (notices, consent, governance, vendor, rights, breach and SDF documents), a placeholder registry, applicability flags, shared blocks, a validation checklist, seven register layouts and a browser "Document Studio" that fills them. The instruction was to use these exact templates and not change them. This ADR replaces decisions 13 (for the document pack only) and 14 of ADR-0009. C26 in `docs/DUATF-Coding-Plan.md` is revised to match.

| # | Decision | Why | Consequence |
|---|---|---|---|
| 1 | **The library is copied into DUATF byte for byte**, in its own folders, under `packages/platform-documents/library/`: the README, `00-common`, the seven template folders, `registers` and the Studio's `ui/engine.js`, `ui/clauses.js` and `ui/data.js`. A manifest holds each file's SHA-256 | The wording is ComplyX's legal drafting; nobody but ComplyX changes it | A test fails the gate if a file differs from its manifest entry. `pnpm duatf templates import <zip>` is the only way in: it lists the added, changed and removed files and rewrites the manifest |
| 2 | **DUATF reads the library the way the Studio's bundler does** (`tools/build_ui.py`): front matter, shared blocks, the registry, the flags tables and the order of each collection's fields | One reading of the files, not two | Checked against the Studio's own bundle, `ui/data.js` |
| 3 | **The grammar is the library's own:** INCLUDE, drafting notes, IF / NOT / == / !=, REPEAT, comments, placeholders, with dates written as "13 May 2027" and `Pre-May-2027` set from the date | A second interpretation of the grammar would print different documents from the same template | TypeScript port of `ui/engine.js`, tested against it on all 37 templates with random inputs. The same applies to `ui/clauses.js` for the clause view |
| 4 | **Each client has a document profile.** Saved flags, common details, collections and per-document values are stored as the library names them (`client_document_profile`). Where DUATF already holds an answer, that answer is the pre-fill and carries its source: SDF status, children's data, transfers abroad and sector from the client profile and the RoPA; contacts from the profile; Processing-Activities and Retention-Schedule from the RoPA; Sub-Processors from the processor register; DPIA-Risks from the DPIAs. A saved value always wins | The consultant enters each value once, and DUATF's registers stay the source of truth | The mapping from DUATF records to placeholder names is one table in code, tested on a worked client |
| 5 | **Documents about one record are built from that record:** B02 and B03 from a breach, R04 letters from a rights request, G05 from a DPIA, V01 and V03 from a processor, G06 from the RoPA | The registers already hold most of what these documents ask for | C23 gains the few fields B02, B04 and the rights log ask for that the registers lacked (C23.6) |
| 6 | **Part A of the library's checklist runs on every render.** A check marked "block release" stops the Word, HTML, Markdown and ZIP downloads until it is fixed; a warning is listed. Preview always works, with blanks highlighted | The checklist is the library's own rule for release | Part B is the consultant's statutory checklist, ticked and signed per document; Part C is shown on the pack page for counsel |
| 7 | **Formats: real `.docx`, Markdown, HTML and a print page; the pack as a ZIP.** The Word file is built from the rendered Markdown (headings, paragraphs, lists, tables, bold and italics) with the `docx` library | The Studio saves HTML under a `.doc` name, which Word opens with a warning; consultants edit these deliverables | The text of the Word file equals the rendering, which a test checks |
| 8 | **Legal review status is per template version.** A template is "awaiting legal review" until an Administrator marks that file reviewed, stored against its SHA-256, so a new library version asks for review again. Until then the Word file carries "Draft: awaiting legal review" in its page header, never in the body | The library itself asks counsel to re-check marked clauses; the template wording stays untouched | `document_template_review`; the header disappears once reviewed |
| 9 | **`[Server-name]` is the firm, ComplyX.** The library's own check A4 keeps it out of public and regulator documents | The library uses it for the preparer in document-control blocks | Taken from the firm's name in DUATF's settings |
| 10 | **Every download is logged:** who, which client, which document or record, which format and which template version | The Studio keeps an export history; a deliverable's provenance matters | `document_export` |
| 11 | **The registers workbook (C25.6) and the public request page (C27.4) use the library as given:** its seven register column layouts and the R03 intake wording | Same rule: the library is the wording and the layout | Columns DUATF has no data for are left blank |
